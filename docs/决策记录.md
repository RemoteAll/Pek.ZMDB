## 2026-11-27 · 大小写口径与 C# 对照审计

### 用户原话

「当前项目大小写相关和C#一致吧」

### 结论

**核心大小写语义与 C# 一致**；另有 3 处边界差异（2 处更宽松、1 处更窄）与 2 处超集，均已记录：

| 行为 | C# 实现 | Zig 当前实现 | 一致？ |
|---|---|---|---|
| 文本精确查询 `FindBy` | 基础索引用原值（`StringIndex.cs:36` + `TypedIndexBase.cs:11/51`，默认比较器） | `find` 用 exact 哈希（`index.zig:209`） | ✅ 都区分大小写 |
| 文本模糊 `FindByLike` | 小写索引 + 小写 pattern（`StringIndex.cs:39/117`） | 小写有序索引 + 小写 pattern（`index.zig:329/422`） | ✅ 都不区分（非 ASCII 见下） |
| 文本范围 `FindByRange` | 小写索引 + `OrdinalIgnoreCase`（`StringIndex.cs:81-89`） | 小写有序索引区间（`index.zig:229-231`） | ✅ 都不区分（非 ASCII 见下） |
| 单字段唯一 | `ConcurrentDictionary<object,long>` 默认相等（`UniqueConstraintManager.cs:15/157`） | `Key.text` 精确比较（`value.zig:71`） | ✅ 都区分大小写 |
| 复合唯一 | `ToString()` 后用 `\|` 拼接（`UniqueConstraintManager.cs:329`） | 类型化键数组，逐键精确比较 | ✅ 都区分大小写（Zig 无 `\|` 拼接歧义） |
| 字段/属性名 | `GetProperty(name)` 严格（`ReflectionUtil.cs:65/79`、`TypedIndexManager.cs:205`） | 索引/唯一表按声明名精确查（`table.zig` 的 `fieldKind`/`findDeclaredField` 精确分支） | ✅ `"id"`/`"name"` 均查不到，`"Id"`/`"Name"` 可查（探针实测） |
| 非 ASCII 折叠 | `ToLowerInvariant()`（Unicode 全量） | `std.ascii.toLower`（仅 ASCII，`index.zig:422`） | ❌ 更窄：`Ä`/`ä` 在 Zig 的模式/范围/小写精确里不折叠 |
| 空串文本索引 | `string.IsNullOrEmpty` 跳过（`StringIndex.cs:33/48`） | 空文本作为键建索引（Rust 版口径） | ❌ 更宽：`findBy("Status","")` Zig 有结果、C# 为空 |
| 加载 JSON 键名 | `JsonObject : Dictionary<String,Object>` 默认比较器（`JsonObject.cs:8`、`TypedDeserializeHelper.cs:104`） | 精确优先、忽略大小写兜底（`entity.zig`/`table.zig` 的 `findDeclaredField`） | ❌ 更宽：小写键 `id`/`username` 也能读入 |
| `?` 通配 | `IsWildcardMatch` 只处理 `*`（`StringIndex.cs:196+`） | 支持 `?` 单字符（`index.zig:396`） | 超集（不影响 C# 数据） |
| 布尔模式中文 | 模式查询仅 true/1/yes/on（`BooleanIndex.cs:45-52`）；归一化支持 是/真/否/假（`:115-120`） | 模式与归一化均支持 是/否（`value.zig:305`） | 差异（Zig 模式超集、归一化缺 真/假） |

### 探针实测（临时用例，跑完已删除）

`zig test --test-filter PROBE` 全绿，确认 Zig 当前行为：

1. `findBy("id")` / `findBy("name")` 返回空（字段名严格大小写，与 C# 一致），`findBy("Id")` 命中；
2. 空文本进索引：`findBy("Status","")` 返回 1 行；C# 为 0 行；

## 2026-11-27 · 双向热更新（文件 ⇄ 内存，三方合并）

### 用户原话

- 「目前是支持文件和内存都能相互热更新加载的吧」
- 「应该是以文件中的为准吧，如非必须一般不会手动改」
- 「那是不是可以对比同时保存呢？只是如果内存和文件中刚好改的是文件的则以文件为准」

### 结论

内存 → 文件原本就支持（脏标记 + 500ms 写合并 + `flush` / `deinit`）；本轮补上 **文件 → 内存热加载**。

冲突策略按用户口径：**逐行对比，只有两边都改的行以文件为准**（不是整表覆盖）：

| 内存 | 文件 | 结果 |
|---|---|---|
| 未改 | 未改 | 不动 |
| 未改 | 改了 | 采用文件 |
| 改了 | 未改 | **保留内存**，并把合并结果写回文件（「对比同时保存」） |
| 改了 | 改了 | **文件优先**（warn） |
| 新增 | 无 | 保留内存新增 |
| 删除 | 未改 | 保持删除 |
| 删除 | 改了 | 文件优先（恢复该行） |

### 实现要点

- `persist.FileSignature`：`mtime + size` 签名，未变化时只做一次 `stat`（变化驱动，不轮询、不整表重读）。
- `Table.synced`：`ID → 上次与文件一致时的行内容哈希`（`entityHash` 零分配，JSON 字段忽略字符串外空白，
  时间按秒，与落盘精度一致）；`load` / `saveTo` 后重建。
- 抽出锁内原语 `updateLocked` / `deleteLocked` / `installRowLocked` 供热加载逐行应用，避免重复实现。
- API：`db.reload(T)`、`db.reloadAll()`、`DbOptions.reload_on_read_interval_ms`（默认 0 = 关闭；
  >0 时读入口按节流检查，`shouldCheckReload` 用毫秒时间戳去重）。
- 自身写盘后更新签名与基准，避免把自己的写入误判为外部变化。
- 文件缺失 / 读失败 / 解析失败：保留内存数据并返回 `error.PersistError`（日志 warn，含路径与错误名）。

### 测试（新增 4 个，基线 66）

- 合并：内存独有保留 / 文件独有采用 / 冲突取文件 + 合并结果写回文件；
- 文件损坏：返回 `error.PersistError`，内存数据不变；
- 读入口自动检查（`reload_on_read_interval_ms = 1`）：等过节流后读到文件值；
- `reloadAll`：返回重载表数，纯内存实例返回 0。

## 2026-11-27 · 性能优化与缺陷修复（不再追求全量 C# 对齐）

### 用户原话

「请继续，而且你现在不是完全要对齐C#版本，而是要提高性能以及修复存在的问题」

### 结论

目标改为**性能 + 修复**，不再逐项对齐 C#（大小写口径审计结论保留为文档，不改语义）。

### 性能改动（全部有实测）

| 改动 | 内容 |
|---|---|
| 负数墓碑删除 | `ordered.IdSet` 删除不再 `orderedRemove`（10 万元素的桶每删一行搬移 ~400 KB），改为 `ids[i] = -id`（比较按绝对值，排序不变），墓碑 ≥ 64 且不少于存活数时原地压缩；新增 `live` 计数保持 `count()` O(1) |
| 表级升序 ID 表 | `Table.ids`（升序 + 墓碑）：`findAll` / 分页（无排序字段）/ 落盘快照直接顺序遍历，**不再每次排序 10 万个 ID** |
| 批量插入预留容量 | `insertBatch` 一次性 `ensureUnusedCapacity`（by_id + ID 表） |
| 更新按字段 diff 快路径 | `value.maybeEqualRaw`：同类型原值相等即跳过 `normalize`（每次更新省掉未变化字段的两次分配） |
| 文本索引零分配 | 短文本（≤128 B）小写键走**栈上折叠 + 有序树查找**，重复值（状态/分类）不再每次 insert/remove 分配 |
| 加载预留容量 | 加载数组时预分配 `by_id` 与 ID 表容量，减少增长期 rehash |

### 缺陷修复

- **`pageBySortField` 释放未初始化内存**：`defer` 遍历整块 `rows`，`normalize` 中途失败（OOM）时会把未初始化槽位当 `?Key` 解引用 → 现在只释放 `rows[0..count]`。属真实崩溃隐患，非风格问题。

### 实测（`zig build bench -Doptimize=ReleaseFast`，10 万行，同机多次取值）

| 场景 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| 删除 ×2 万 | 287 ms（14 µs/次） | 46 ms（2.3 µs/次） | **6.2×** |
| 分页（按 ID）×20 | 100 ms（5 ms/次） | < 1 ms | **>100×** |
| 更新单字段 ×2 万 | 38 ms | 31 ms | 1.2× |
| 加载 8 万行 + 全表读取 | 293 ms | 279 ms | 1.05× |
| 批量插入 10 万行 | 246~259 ms | 243 ms | 持平（未回退） |
| 文本前缀查询 ×20 | 89 ms | 76 ms | 1.17× |

> 插入曾一度回退到 296 ms（+20%）：A/B 实测定位到「并行墓碑标志数组」的额外写入（每行 × 6 个索引各多一次 append），
> 改为负数墓碑（零额外存储）后恢复并略优于基线 —— 结论是**测量出来的，不是推算的**。
